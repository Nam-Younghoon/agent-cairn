# /pr-reviewer — Pull Request 상세 리뷰

이 프롬프트는 Codex CLI 에서 `/pr-reviewer <PR번호> [추가 메시지]` 호출 시 Claude Code 의 동명 슬래시 커맨드와 **동일한 흐름**으로 동작합니다. Codex 에서는 커스텀 슬래시 커맨드 자동 바인딩이 확정되지 않았을 수 있으므로, 바인딩되지 않으면 `@.codex/prompts/pr-reviewer.md 의 절차를 따라 PR <번호> 를 리뷰해주세요` 같이 파일 참조로 사용하세요.

입력: `<PR번호> [추가 메시지]`

이 커맨드는 `/discuss → /plan → /execute → /ship` 파이프라인과 **독립된 별도 트랙**입니다. 이미 올라온 PR 을 대상으로 동작하며, 브랜치 분기·코드 수정·커밋을 수행하지 않습니다.

> **Codex 세션 주의사항**
> 1. `.env`·시크릿 쓰기 차단 훅이 없으므로, 보고서·코멘트에 시크릿 후보 문자열이 들어가지 않도록 본 흐름의 시크릿 마스킹 절차를 **반드시** 수행한다.
> 2. `approval_policy="on-request"` 환경에서는 `gh` CLI 호출 시 사용자 승인 프롬프트가 뜰 수 있다. 처음 사용 시 한 번 안내한다.

---

## 1단계. 인자 파싱

- `$ARGUMENTS` 를 공백 기준으로 분할.
  - 첫 토큰 = PR 번호 (필수). 숫자가 아니면 사용법을 출력하고 중단.
  - 나머지 토큰 = 사용자 추가 메시지 (선택). 비어 있으면 빈 문자열.
- `$ARGUMENTS` 에 `--repo` 플래그가 포함되어 있으면 **즉시 중단**. 본 사이클은 현재 디렉토리 origin 만 지원한다 (ADR-010). 안내 메시지: "외부 레포 리뷰는 미지원입니다. 해당 레포로 cd 후 다시 호출해 주세요."
- 둘을 변수로 보관하고, 사용자에게 "PR #<번호> 리뷰를 시작합니다" 한 줄 알림.

## 2단계. 사전 검증

다음을 **순서대로** 확인하고, 하나라도 실패하면 명확한 안내 메시지와 함께 중단한다.

1. 현재 디렉토리가 git 레포인지: `git rev-parse --show-toplevel`
2. `gh` CLI 가용성: `gh --version` (없으면 `https://cli.github.com` 안내)
3. `gh` 인증 상태: `gh auth status` (실패 시 `gh auth login` 안내)
4. 현재 디렉토리의 origin 이 GitHub 레포인지: `gh repo view --json url` 가 성공해야 함
5. 지정된 PR 번호가 실제로 존재하는지 + 상태가 `OPEN` 인지:
   - `gh pr view <번호> --json number,state,headRefOid` 로 메타 수집 (실패 메시지 그대로 전달)
   - `state` 값을 확인: `OPEN` 이 아니면(`CLOSED`/`MERGED`) line-level 코멘트 게시가 실패할 수 있음을 사용자에게 안내하고, "그래도 로컬 리뷰만 진행할까요?" 컨펌. 거절 시 중단, 승인 시 6단계의 게시 옵션을 dry-run 으로 강제.
   - `headRefOid` 는 7-1 단계에서 `commit_id` 로 사용하므로 변수에 보관.

## 3단계. 리뷰 수행

**아래 `## 인라인 가이드 — PR 리뷰` 절차를 직접 수행**한다. Claude 의 `pr-reviewer` 서브에이전트와 동일한 4단계(컨텍스트 수집 → 요구사항 검증 → 사이드 이펙트 분석 → 전사 재검수) 를 Codex 단일 세션에서 그대로 수행한다.

결과로 두 가지를 만든다.
- 보고서 마크다운 본문 (4단계에서 저장할 본문)
- 콘솔용 요약 한 줄

## 4단계. 보고서 저장

3단계에서 만든 마크다운 본문을 **`__docs/pr-review-<PR번호>.md`** 로 저장한다.
- 디렉토리 없으면 생성.
- 동일 PR 을 재리뷰한 경우 **덮어쓴다** (ADR-012).
- **저장 전 시크릿 후보 grep 재검**: `password=`, `secret=`, `token=`, `Bearer `, `AKIA`, JWT 패턴 등이 본문에 마스킹되지 않은 채 남아있는지 확인. 발견 시 마스킹하거나 사용자에게 보고 후 중단. (Codex 세션은 시크릿 차단 훅이 없으므로 이 단계가 유일한 안전망이다.)

## 5단계. 콘솔 요약 출력

```
판정: PASS | BLOCK  /  BLOCK <N>건, WARNING <M>건  /  주요 사유: <한 줄>
보고서: __docs/pr-review-<PR번호>.md
```

## 6단계. PR 코멘트 게시 컨펌 (사용자 승인 필수)

사용자에게 다음을 묻는다.

```
이 리뷰 결과를 PR #<번호> 에 코멘트로 게시할까요?
  - BLOCK 사유는 해당 라인에 line-level 코멘트로 남깁니다 (gh api)
  - 종합 코멘트는 PR 일반 코멘트로 게시합니다 (gh pr comment)
  옵션: yes / no / dry-run (게시할 문구만 보여주고 실제 게시는 보류)
```

- `no` 또는 거절: 로컬 보고서 경로만 안내하고 종료.
- `dry-run`: 게시할 문구(line-level 본문 + 종합 코멘트 본문) 를 콘솔에 출력하고 종료.
- `yes`: 7단계로.

## 7단계. PR 코멘트 게시 (gh CLI)

### 7-1. Line-level 코멘트 (BLOCK 사유)

판정이 BLOCK 이면, 보고서의 BLOCK 항목별로 `gh api` 를 호출해 해당 파일/라인에 코멘트를 남긴다.

**쉘 인젝션 방지**: 본문에는 마크다운이 포함되므로 `"`, 백틱, `$()`, 개행이 들어갈 수 있다. 절대 `-f body="..."` 로 인라인 전달하지 말고, **임시 파일에 본문을 쓴 뒤 `-F body=@<임시파일>` 로 전달**한다.

```
TMP=$(mktemp)
printf '%s' "<사유 + 권장 수정 본문>" > "$TMP"
gh api repos/<owner>/<repo>/pulls/<번호>/comments \
  -F body=@"$TMP" \
  -f commit_id="<2단계에서 보관한 headRefOid>" \
  -f path="<파일 경로>" \
  -F line=<번호> \
  -f side="RIGHT"
rm -f "$TMP"
```

- `<owner>/<repo>` 는 `gh repo view --json nameWithOwner -q .nameWithOwner` 로 추출.
- 한 BLOCK 사유당 한 번씩 호출. 실패 시 사용자에게 보고하고 다음 항목 진행.

판정이 PASS 면 7-1 은 건너뛴다.

### 7-2. 종합 코멘트 (`gh pr comment`)

**쉘 인젝션 방지 + 길이 제한(GitHub 65,536자) 회피**를 위해 항상 `--body-file` 로 파일을 직접 전달한다.

```
TMP=$(mktemp)
# 아래 규칙으로 "$TMP" 에 본문 작성
gh pr comment <번호> --body-file "$TMP"
rm -f "$TMP"
```

본문 규칙:
- **PASS**: 정확히 다음 한 줄을 게시한다.
  ```
  코드 리뷰는 통과입니다. 실기기 테스트 진행 후 Merge 진행해도 좋습니다.
  ```
  WARNING 항목이 1건 이상이면 위 한 줄 뒤에 빈 줄을 두고 `### 권고 사항` 섹션으로 WARNING 요약을 한 문단 추가.
- **BLOCK**: 다음 형식으로 게시한다.
  ```
  ## 코드 리뷰 결과: BLOCK

  <BLOCK 사유 요약 3~5줄>

  ### BLOCK 항목
  - [<카테고리>] <path>:<line> — <사유>
  - ...

  ### 권장 후속 조치
  - <조치 1>
  - <조치 2>

  상세 line-level 코멘트는 변경 파일에 별도 게시되었습니다.
  ```

### 7-3. 결과 보고

게시 성공/실패 개수를 사용자에게 한 줄로 보고하고 종료.

```
PR #<번호> 코멘트 게시 완료: line-level <N>건, 종합 1건
```

## 금지

- 사용자 승인 없이 PR 코멘트를 게시하지 않는다 (ADR-009).
- 리뷰 결과를 git 커밋·푸시 형태로 만들지 않는다 (본 커맨드는 로컬 산출물 + PR 코멘트만 다룬다).
- 시크릿 원문 값을 보고서·PR 코멘트에 노출하지 않는다 (마스킹 필수). Codex 세션은 시크릿 차단 훅이 없으므로 본 커맨드가 유일한 안전망이다.
- 본 커맨드가 다루는 PR 의 코드를 직접 수정하지 않는다.
- 외부 레포(현재 디렉토리 origin 외) 는 본 사이클 비지원. `--repo` 옵션이 지정되어도 거절한다 (ADR-010).
- `gh pr review --approve` / `gh pr merge` 등 머지·승인 액션을 수행하지 않는다.
- 보고서 파일을 `__docs/` 외부에 저장하지 않는다 (`.gitignore` 보호 보장).
- `gh pr comment --body "..."` 또는 `gh api -f body="..."` 처럼 코멘트 본문을 **인라인 문자열로 전달하지 않는다**. 항상 `--body-file <파일>` 또는 `-F body=@<파일>` 로 파일을 통해 전달한다 (쉘 인젝션 + 길이 제한 회피).

## 인라인 가이드 — PR 리뷰

Claude 의 `pr-reviewer` 서브에이전트를 Codex 세션에서 직접 대체하는 절차. **변경 코드 + 관련 코드(역참조)** 를 모두 읽고 PASS|BLOCK 판정 보고서를 만든다.

### 작업 순서

#### 1. 컨텍스트 수집
- `gh pr view <번호> --json title,body,headRefName,baseRefName,files,labels,author,url` 로 PR 메타데이터 수집.
- `gh pr diff <번호>` 로 전체 diff 수집.
- 변경된 파일 목록을 추출하고, **각 파일을 전체 정독**한다 (diff 의 컨텍스트 라인만으로는 부족).
- 변경된 공개 심볼(함수/타입/엔드포인트/엑스포트) 을 추출하고 `grep`/`rg` 로 **호출 위치를 모두 역추적**한다 (reverse references).
- 역참조된 파일도 정독한다 — 변경이 그 호출자에게 미치는 영향을 판단해야 한다.

#### 2. 요구사항 충족도 검증
- PR 본문, 연결된 이슈(있다면 `gh issue view`), 그리고 호출 시 전달된 추가 메시지에서 **요구사항 목록** 을 추출한다.
- 각 요구사항을 "충족 / 부분 충족 / 미충족" 으로 매핑하고, 근거가 되는 파일:라인을 명시한다.
- 미충족 항목은 BLOCK 후보.

#### 3. 사이드 이펙트 분석
변경이 야기할 수 있는 영향을 아래 카테고리로 빠짐없이 점검한다.
- **시그니처 변경**: 함수/엔드포인트/타입의 입출력 변화가 호출자에 미치는 영향.
- **데이터 흐름**: 상태·트랜잭션 경계·캐시·이벤트 흐름의 변화.
- **의존성**: 새 패키지 추가, 버전 업, 환경변수 추가 (`.env.example` 갱신 여부 확인).
- **DB 스키마**: 마이그레이션 파일 존재 여부, 안전한 서브커맨드 사용 여부.
- **보안**: 하드코딩된 시크릿, 입력 검증 누락, 권한 검사 누락, OWASP Top 10 위반.
- **성능·동시성**: N+1 쿼리, 락 범위, 재시도 폭주 가능성.
- **실패 모드**: 에러 처리 누락 또는 과도한 try/catch.

각 항목은 "어떤 변경이 → 어떤 영향 → 어떤 근거(파일:라인)" 형식으로 적는다.

#### 4. 전사 재검수
1~3 단계 결과를 모아 한 번 더 훑으면서 **놓친 영향 범위** 를 재확인한다. 새로 발견된 항목을 BLOCK / WARNING / INFO 로 분류해 보고서에 추가한다.

### 판정 규칙

#### BLOCK (아래 중 하나라도 해당하면 BLOCK)
- 요구사항 미충족 또는 명백한 로직 결함
- 보안·시크릿 누출 (하드코딩, OWASP, 입력 검증 누락, 권한 검사 누락)
- 하네스 규약 위반 (TypeScript `any`, 시크릿 하드코딩, 줄임말 네이밍, `.env.example` 갱신 누락, 운영 DB 파괴 명령, 마이그레이션 도구 우회 등)

#### WARNING (BLOCK 아님 — 권고)
- TDD 누락 (신규 로직에 테스트가 없거나 실패 케이스 미커버)
- 가독성·네이밍 개선 여지
- 사이드 이펙트가 있으나 현재 PR 범위에서 정당화되는 변경

#### PASS
- BLOCK 0건이면 PASS. WARNING 개수는 PASS 와 무관 (보고서에는 기록).

### 시크릿 마스킹
diff 본문에 `password=`, `secret=`, `token=`, `Bearer `, `AKIA`, AWS 키 패턴, JWT 패턴이 발견되면 보고서에 인용할 때 값을 `***MASKED***` 로 치환한다. 시크릿 자체는 BLOCK 사유로 기록하되 원문 값을 보고서에 노출하지 않는다.

### 출력 포맷

```markdown
# PR #<번호> 리뷰 보고서

- **PR**: <title> ([링크](<url>))
- **작성자**: <author>
- **헤드 → 베이스**: <headRefName> → <baseRefName>
- **판정**: PASS | BLOCK
- **리뷰 일시**: <ISO 8601>
- **요약**: <3~5줄>

## 요구사항 충족도

| 요구사항 | 충족 여부 | 근거 |
| --- | --- | --- |
| ... | ✅ / ⚠️ / ❌ | <path>:<line> |

## BLOCK 항목 (있을 때만)
- [카테고리] <path>:<line> — 사유 + 권장 수정

## WARNING 항목 (있을 때만)
- [카테고리] <path>:<line> — 권고

## 사이드 이펙트 분석
- 시그니처 변경: ...
- 데이터 흐름: ...
- 의존성: ...
- 보안: ...
- 성능·동시성: ...
- 실패 모드: ...

## 전사 재검수 메모
- <놓치기 쉬웠던 항목 / 추가 발견>

## 점검에 사용한 명령
- gh pr view <번호> --json ...
- gh pr diff <번호>
- grep 으로 역참조 검색한 심볼: <목록>
```

콘솔용 요약 한 줄도 함께 만든다.

```
판정: PASS | BLOCK  /  BLOCK <N>건, WARNING <M>건  /  주요 사유: <한 줄>
```

### 금지
- 리뷰 단계에서 코드 파일을 수정하지 않는다. 모든 권장 수정은 보고서 텍스트로만 표현한다.
- 리뷰 단계에서 `gh pr comment`, `gh pr review --comment`, `gh api .../comments` 등 **PR 에 코멘트를 게시하지 않는다**. 코멘트 게시는 메인 흐름의 7단계에서 사용자 승인 후에만 수행한다.
- `git commit`, `git push` 등 git 상태 변경 명령을 실행하지 않는다 (조회용 `git log`, `git diff` 는 허용).
- 추측을 사실처럼 보고하지 않는다. 확인되지 않은 영향은 "추가 확인 필요" 로 분류한다.
- 사용자에게 직접 질문하지 않는다. 정보 부족 시 보고서의 "추가 확인 필요" 섹션에 기록하고 메인 흐름으로 돌아가 처리한다.
- 시크릿 원문 값을 보고서 본문에 그대로 인용하지 않는다 (마스킹 필수).
